# State Machine Analysis

## 目标

把“先做 A，再做 B，满足条件后做 C”的模糊流程，转化成可验证的状态转换逻辑。

## 什么时候触发

- 预充流程；
- 主接触器闭合/断开；
- 上电、启动、运行、停机；
- 充电/放电状态切换；
- 故障、降额、恢复；
- 控制器存在超时、联锁、互锁；
- 需要检查“为什么没有进入下一步”。

## 核心元素

每个状态至少定义：
- State：状态名称；
- Entry Condition：进入条件；
- Entry Action：进入动作；
- Hold Condition：保持条件；
- Observables：可观察量；
- Exit Condition：退出条件；
- Transition：下一状态；
- Timeout：超时；
- Fault Transition：故障跳转；
- Recovery：恢复条件。

## 第 1 步：确定状态，不要先画箭头

状态应表达“系统当前处于什么稳定/可识别阶段”，而不是单个瞬时动作。

例如：
- OFF
- SELF_CHECK
- PRECHARGE
- READY_TO_CLOSE
- RUN
- FAULT
- SHUTDOWN

“闭合 KM1”通常是动作，不一定是独立状态。

## 第 2 步：定义状态变量和观测量

明确控制器依据什么判断：
- 电压；
- 压差；
- 电流；
- 辅助触点；
- 绝缘状态；
- 通信状态；
- 温度；
- SOC；
- 计时器；
- 故障码。

把“真实物理量”和“控制器内部状态”分开。

## 第 3 步：定义转换条件

每一条箭头都必须回答：
- 什么条件触发；
- 条件持续多久；
- 是否有滞回；
- 是否需要多个条件同时满足；
- 条件来自哪个传感器/信号；
- 信号无效时怎么处理。

不要写“电压接近后进入下一步”这种不可测试条件。

## 第 4 步：检查动作与反馈

每个关键动作都要有反馈确认，例如：
- 发出接触器闭合命令；
- 读取辅助触点；
- 检查母线电压/电流是否符合预期；
- 超时则进入故障。

命令已发出 ≠ 动作已完成。

## 第 5 步：分析超时与异常跳转

重点检查：
- 预充超时；
- 接触器拒动；
- 接触器粘连；
- 电压不上升；
- 电流异常；
- 通信丢失；
- 传感器失效；
- 状态跳变；
- 恢复条件不完整。

所有“正常路径”都应配至少一个异常路径。

## 第 6 步：检查互锁与不可达状态

检查：
- 两个互斥动作是否可能同时发生；
- 是否存在永远无法进入的状态；
- 是否存在进入后无法退出的状态；
- 是否存在循环跳转；
- 故障恢复是否会绕过必要检查；
- 上电初始状态是否确定。

## 第 7 步：用时间线验证

至少跑三条：
1. 正常路径；
2. 一个典型故障路径；
3. 一个边界/超时路径。

记录：
t0 状态、输入、命令、反馈、下一状态。

## 第 8 步：输出

推荐输出：
- 状态表；
- 转换表；
- 正常时序；
- 异常时序；
- 待确认信号；
- 可测试判据。

## 预充示例骨架

OFF
→ 满足上电/允许条件
→ PRECHARGE
→ 预充支路投入
→ 监测 DC-link 压差
→ 压差低于阈值且其他联锁满足
→ MAIN_CONTACTOR_CLOSE
→ 反馈确认
→ RUN
→ 若超时/拒动/压差异常
→ FAULT

注意：预充的对象通常是母线电容和相关 DC-link，不是“给电池充电”。

## 与其他 Skill 的关系

- 用 `system-modeling` 先确认主功率链和控制边界；
- 用 `feedback-loop-analysis` 分析控制反馈；
- 用 `test-plan-design` 把状态转换条件变成测试用例；
- 用 `evidence-verification` 区分已确认逻辑与待确认信号。

## 边界

- 未确认阈值、超时、端子和逻辑不得脑补；
- 状态机是控制逻辑模型，不自动代表实际硬件动作成功；
- 对安全关键系统，最终状态逻辑须由受控设计文件/代码/测试验证。
